# Server-first Ordexa Stores — 5.59.0 / Server 2.8.0

## Πρωτόκολλο και αποθήκευση

Οι αναλυτικές παραγγελίες, διορθώσεις/παρατηρήσεις και επιβεβαιωμένες απουσίες παραμένουν στην ιδιωτική SQLite `store_billing_local`. Οι δύο πλήρεις συνεπείς λήψεις Ordexa, οι σταθερές ταυτότητες, οι ανεξάρτητοι όροι Fleet, η ημέρα [05:00, επόμενη 05:00) Europe/Athens και η προαιρετική διατήρηση ανά κατάστημα (OFF αρχικά) διατηρούνται. Η αποδοχή σελίδας χρησιμοποιεί τοπική συναλλαγή. Δεν γίνεται καμία εγγραφή στο Ordexa.

Η ολοκλήρωση ημέρας αποθηκεύει ατομικά τοπικά αποτελέσματα, ιστορικό επιβεβαιωμένων αφαιρέσεων, κάλυψη και αμετάβλητο στιγμιότυπο outbox. Η αναλυτική εγγραφή δεν διαγράφεται: αλλάζει η ενεργή κατάστασή της και κρατείται audit. Χειροκίνητο αίτημα από τον Server αποθηκεύεται τοπικά, χωρίς να χρειάζεται D1. Αποτυχία ελέγχου cloud οδηγεί σε τοπική άντληση με αποθηκευμένους όρους· σε πρώτη εγκατάσταση χρησιμοποιούνται προσωρινά οι αρχικοί Ordexa όροι, με υποχρεωτικό έλεγχο ανεξάρτητων Fleet όρων πριν δημοσίευση.

Η ουρά επιχειρεί δημοσίευση ανά πέντε λεπτά. Αποστέλλονται έως 32 αλλαγμένα αποτελέσματα ανά σελίδα. Το σημασιολογικό hash εξαιρεί χρόνο ανάγνωσης και runId. Ένας χωριστός, χωρίς mirror triggers, πίνακας D1 κρατά μόνο προσωρινές συγκεντρωτικές σελίδες. Η δημοσίευση ελέγχει epoch/restore fence, generation, αναθεώρηση όρων, κάθε storeRevision/retentionUsed, πλήρη κάλυψη καταστημάτων και τη συγκεκριμένη προηγούμενη δημοσίευση, και αλλάζει τα ορατά αποτελέσματα ατομικά. Τα αμετάβλητα ημερήσια αποτελέσματα δεν ξαναγράφονται. Κρατείται receipt για επανάληψη μετά από χαμένο ACK. Η αποστολή δεν εξαρτάται από lease μεγάλης διάρκειας ή από αναλυτικές παραγγελίες D1.

Τα προϋπάρχοντα παραγωγικά records παραμένουν. Οι προβολές διαβάζουν τόσο την παλιά δημοσίευση όσο και τις νέες σταθερές συγκεντρωτικές εγγραφές. Μετά τη διαπραγμάτευση `protocol:2` ο Worker απορρίπτει παλιό raw archive/stage/publish για την ίδια σύνδεση. Η εφεδρική πρόσβαση #52 διατηρείται και αναγνωρίζει τις σταθερές συγκεντρωτικές εγγραφές.

## Αστοχίες, μετάβαση και επαναφορά

- D1 unavailable/quota: η εισαγωγή ολοκληρώνεται τοπικά· το cloud κρατά το τελευταίο επιβεβαιωμένο αποτέλεσμα. Ο Server εμφανίζει χωριστά τοπική ολοκλήρωση και αριθμό εκκρεμών ημερών.
- Απώλεια απάντησης: επανάληψη του ίδιου snapshot/receipt, χωρίς δεύτερη χρέωση ή αναλυτική αποστολή.
- Αλλαγή τιμών/διατήρησης/epoch: η δημοσίευση απορρίπτεται, διατηρείται η ουρά και ζητείται νέα λήψη όρων/υπολογισμός της συγκεκριμένης ημέρας.
- Πρώτη μετάβαση: γίνεται πλήρης ανάκτηση του παλιού D1 archive, χωρίς αντικατάσταση υπάρχουσας τοπικής αποδεκτής παραγγελίας. Marker γράφεται μόνο αφού ολοκληρωθεί όλη η ανάκτηση, ώστε διακοπή στη μέση να μη θεωρηθεί πλήρης μετανάστευση.
- Νέα συσκευή όταν το cloud έχει ήδη server-primary ιστορικό: απαιτείται πλήρες backup του προηγούμενου Server πριν επιτραπεί δημοσίευση. Δεν θεωρείται ότι οι παραγγελίες που λείπουν από το Ordexa ή από το παλιό D1 archive δεν υπήρξαν.
- Επαναφορά: πρώτα επικύρωση όλων των records, έπειτα τοπική συναλλαγή. Οι τοπικές ημερήσιες προβολές μπαίνουν ξανά σε ουρά ανανέωσης· παλιά leases/ACK/epoch δεν θεωρούνται έγκυρα.

## Backup

Ο υπάρχων κρυπτογραφημένος μηχανισμός `.fcbackup` περιλαμβάνει όλες τις αναλυτικές παραγγελίες, όρους, audit, κάλυψη και τοπικά ημερήσια αποτελέσματα. Διατηρούνται AES-GCM, SHA-256, fsync/atomic rename, επικύρωση πριν restore, ιδιωτικό αντίγραφο και επανάληψη εξαγωγής στον ήδη επιλεγμένο φάκελο/Drive. Ο αυτόματος έλεγχος εκτελείται και όταν αποτύχει η ανανέωση mirror. Χωρίς επιλεγμένο φάκελο δημιουργείται επαληθευμένο κρυπτογραφημένο τοπικό αντίγραφο και εμφανίζεται η εκκρεμότητα αντιγράφου εκτός συσκευής. Ισχύουν η υπάρχουσα ρύθμιση συχνότητας/διατήρησης και το όριο ασφαλούς επαναφοράς 50 MB: υπέρβαση αποτυγχάνει ρητά, χωρίς περικοπή. Δεν προστέθηκε επί πληρωμή υπηρεσία ή αποθήκευση raw orders στη D1.

Δεν λήφθηκε backup πραγματικών παραγωγικών δεδομένων από το εργαλείο ανάπτυξης και δεν έγινε φυσική εγκατάσταση στο S24 Ultra. Η παραγωγική λειτουργία του backup εξαρτάται από τη ρύθμιση και τα δικαιώματα του φακέλου στην πραγματική συσκευή.

## Μετρήσεις και έλεγχοι

`node scripts/profile-store-primary.mjs` εκτελεί το πραγματικό SQL σε Miniflare/Workerd D1, με τα παραγωγικά indexes και mirror triggers, και αθροίζει `meta.rows_written`. Συνθετικά δεδομένα: 8 καταστήματα, 100 παραγγελίες/ημέρα. Δεν περιλαμβάνονται setup/control, παραγωγική τηλεμετρία, χρόνοι Ordexa ή φυσικός χρόνος S24.

| 7 | 700 | 4.746 | 672 | 91 |
| 31 | 3.100 | 21.018 | 2.976 | 403 |

Μείωση εγγραφών εισαγωγής **85,84%** στο παραπάνω fixture. Αμετάβλητη επανάληψη: **0** ημερήσιες εγγραφές αποτελεσμάτων, μόνο φρεσκάδα/receipt/guards. Δεν αποτελεί πρόβλεψη συνολικού ημερήσιου λογαριασμού παραγωγής. Συνθετική μέτρηση 30 heartbeat στο ίδιο λεπτό: **31→2 rows written** (−93,55%). Heartbeat αποθηκεύεται το πολύ μία φορά/λεπτό με SQL CAS (εντός υπάρχουσας ανοχής 7 λεπτών). Αμετάβλητες ρυθμίσεις heartbeat/exchange δεν ενημερώνονται ξανά. Progress καταστημάτων περιορίζεται από 30 δευτερόλεπτα σε 5 λεπτά και δεν εμποδίζει την τοπική εισαγωγή. Ο executor καταστημάτων λειτουργεί ανά 250 ms αντί ανά 2 s, χωρίς παράλληλα αιτήματα Ordexa ή αλλαγή ωριαίου/πεντάλεπτου προγράμματος.

Στοχευμένοι έλεγχοι: actual Java/SQLite/provider fixture/Worker, >50 παραγγελίες και explicit shop filtering, incomplete-page rejection, stable double scan, OFF/ON/opt-out retention, no resurrection, source reappearance, lost ACK, πλήρως απούσα D1 κατά την εισαγωγή, επανεκκίνηση και επακόλουθη παράδοση, ψυχρή offline εκκίνηση, migration/restore validation, πραγματικό Workerd D1 aggregate-only publish, αμετάβλητα stable rows, stale terms/source/restore fences, υπάρχον backup cipher/streaming/jobs και direct access. Οι τελικές επιτυχίες CI/υπογραφής/δημοσίευσης καταγράφονται στο handoff και στο GitHub Release.
